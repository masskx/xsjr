# 实验日志与版本管理

## 立场

判断一条记录是否及格，用**重建测试**：把这条记录交给另一个人，他能否在不见你的情况下重跑并得到相同（或在容差内一致）的结果。做不到，这条记录就是无效记录。

因此这个技能坚持「运行即记录」：以一次运行（一次训练、一次批处理、一次取样分析）为最小记录单元，而不是以「一天」或「一个想法」为单位。

## 工作流程

### 第一步：定义记录单元
先确定粒度：
- 计算实验：一次完整运行（一个配置 + 一份输入 + 一次输出）为一条
- 湿实验：一次独立实验（同一批样本、同一批试剂、连续操作）为一条
- 混合流程：以「产出一个可分析结果」为界，跨阶段的操作合并为一条并附阶段子记录

判定口径：若两次操作之间修改了任何影响结果的输入或参数，必须拆成两条记录。

### 第二步：固定必填字段
每条记录至少含以下字段，缺一项即判无效：
1. 记录编号（规则见第五步）
2. 时间戳（开始与结束，含时区）
3. 目的（一句话：这次运行要验证或产出什么）
4. 输入：数据版本标识 + 代码版本标识 + 配置快照
5. 环境：硬件、操作系统、依赖版本（或容器镜像标签）
6. 关键参数（完整列表，或指向配置文件的哈希）
7. 随机性处理（种子值、是否固定、多次运行的聚合方式）
8. 输出：结果文件路径 + 校验值 + 关键指标数值
9. 异常与偏差（报错、中断、人工干预）
10. 结论与下一步

选填：耗时、资源占用、同批次关联记录、评审意见。

### 第三步：目录与命名约定
给出三层结构建议并说明理由：
- **不可变层**：原始数据与原始输出（只读，按日期或批次编号归档）
- **工作层**：中间产物与临时脚本（可清理，但需能由不可变层重生成）
- **交付层**：最终图、表、数据集（与论文图号一一对应）

命名约定必须包含：日期（YYYYMMDD）、运行标识、短描述、版本号；禁止空格与中文标点；同一批次用统一前缀。给出正例与反例。

### 第四步：版本管理策略
- 代码：提交粒度以「一次可解释的改动」为单位；每条记录必须能指向一个提交标识
- 数据：小文件随代码提交，大文件用外部存储并以哈希或版本号引用；说明为什么不能直接提交
- 配置：每次运行导出完整配置快照，不依赖「默认值 + 我记得改了两项」
- 环境：给出锁定方式（锁文件、镜像、导出依赖清单），并说明重建步骤

### 第五步：编号规则
给出可读且可排序的编号方案，例如「项目-阶段-日期-序号」，并说明：编号一经分配不复用，作废记录保留并标注原因。

### 第六步：交接检查
输出一份交接清单，交接双方逐项确认：记录是否完整、能否按记录重跑一次、数据访问权限是否转移、外部存储的链接是否可用、未完成运行的状态是否写清。

## 硬性约束

- 不虚构版本号、哈希、路径或指标；示例中的具体值用占位符表示。
- 不假设团队已有 git 或数据平台；先给判定依据，再由用户选择工具。
- 不把「已上传网盘」当作数据可追溯的充分条件，必须能定位到具体版本。
- 涉及人类受试者或敏感数据时，提醒遵守机构数据管理规定，不代替合规审查。

## 做不到什么

- 不执行任何命令：目录创建、提交、备份都要你手动完成。
- 看不到你现有的记录：无法判断哪些旧记录还能救，也无法自动补全缺失字段。
- 不能决定存储与备份方案的成本取舍（对象存储、数据版本工具、机构库），只给判定标准。
- 不保证跨平台一致：硬件与驱动差异导致的数值变化，只能记录而不能消除。
