# 审稿意见分类归档

## 立场

修回管理的第一原则：**按依赖排序，不按意见顺序排序**。审稿人写意见时不会考虑你的执行约束，因此顺序天然是乱的；把它整理成可并行的任务图，是这个技能唯一的目标。

第二原则：**一条意见可以拆成多个任务，但回复编号必须唯一**。任务可以拆给多人，回复时仍要合回一条，否则编辑核对时会混乱。

## 工作流程

### 第一步：拆条
按「一个可独立完成的动作」拆分。判定口径：如果一条意见需要两个人分别做两件事，就拆成两条任务，但保留同一个意见编号（用 R1-3a、R1-3b 表示）。反之，如果两条意见本质是同一件事（例如都在质疑样本代表性），不要硬拆，合并成一条并注明覆盖了哪几条意见。

### 第二步：打标签（六类）
1. **证据缺口**：必须补数据或补实验才能回应
2. **论证缺口**：需要补分析、补定义、补讨论或限定结论
3. **写作与格式**：措辞、结构、图表编号、语言问题
4. **数据与材料补充**：提供额外数据、代码、补充材料，但不涉及新实验
5. **统计复核**：检验方法、模型设定、多重比较、样本量说明
6. **编辑事务**：作者信息、声明、系统字段、格式模板

标签要单选。若一条意见同时属于两类，按「回应它的最小充分动作」归类——例如审稿人质疑统计方法但只需补一段说明，归为 2 而不是 5。

### 第三步：估工作量与依赖
对每个任务给出：预估工时（半天/一天/三天/一周/需新数据）、前置依赖（等哪个任务、等什么资源）、可并行性。

依赖判定口径：只要 A 的产出是 B 的输入（例如「补的实验结果」是「改结果段」的输入），就必须 A→B；若两者只共享资源（同一台设备），标为资源冲突而非强依赖。

### 第四步：排关键路径
找出最长链，标出「延误一天就整体延误一天」的任务。给出两种排期：正常排期与时间被压缩 30% 时的取舍方案（哪些降级为论证回应）。

### 第五步：回复编号映射
建立映射表：意见编号 → 任务编号 → 回复信中的段落编号。要求一一对应且稳定，后期新增意见用后缀扩展，不重排已有编号。

### 第六步：状态跟踪
给出状态机：待办 → 进行中 → 待审阅 → 已定稿 → 已进回复信。说明每个状态的判定标准与谁有权推进。

## 硬性约束

- 不写回复信正文，只做分诊与排期。
- 不推断审稿人身份、动机或敌意；标签只依据意见内容。
- 不虚构工时与资源可用时间；用户未提供的写 `[待补]`。
- 不合并不同审稿人的意见编号，保持可追溯。

## 做不到什么

- 不判断意见的「真实意图」：那是审稿意见解读类工作的范围，本技能只看可执行动作。
- 不知道你团队的真实效率：工时估算是参考值，需要按实际情况修正。
- 不能替代项目管理工具：输出可导入表格或看板，但状态更新要人来做。
- 不保证排期在设备、样本或合作者延迟时仍可行。
